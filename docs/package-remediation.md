# Package and application remediation

Owner-approved completion plan. Execution is in progress, not complete. The
[execution checklist](package-remediation-status.md) records acceptance evidence
and next actions. Package/repository facts come from the existing registers and
product composition plans; this document is not another package registry.

## Outcome and operating agreement

Every applicable product uses maintained shared behavior through verified release
artifacts. Accounts are predictable, chats respect the reader, product-specific
workflows remain intact, and releases update consumers and public references.
New projects inherit the same package-selection and verification rules.

Routine implementation, regression tests, versioned releases, consumer PRs,
checked merges, compatible migrations, deployments, verification and observation
are authorized. The executing agent owns the queue and resolves failures. Owner
review is not a per-PR step. Escalate only concrete missing authority/credentials,
a paid commitment, an irreversible destructive operation or an unresolved
product/legal decision, after exhausting existing access. Consolidate blockers;
never request secrets in chat or mark blocked work complete.

Use open, implementing, validating, observing, blocked and complete states. Each
task records its affected repositories (privately where necessary), owning
package, prerequisites, frozen target artifact, evidence, next action and blocker.
Distinguish merged, released, deployed and verified. A declaration, import, green
PR or configured provider is not sufficient proof of a working deployment.

## Verification, rollout and closure

Reproduce → fix owner → test built artifact → release → locked consumer update →
exact-commit CI → checked merge → deploy → receipt/journey → observe → promote.

Cover 320/390px and desktop, light/dark, keyboard and screen-reader labels, safe
areas/soft keyboard, touch targets and long/code/table content. Chat tests include
initial following, touch/keyboard, tokens/status, reply completion, optimistic
replacement, draft preservation/clearing, IME, Stop/Retry, attachments and voice.
Account tests include the complete lifecycle, provider callbacks, existing-user
transitions and negative authorization cases. Automation tests cover absent
bindings/receipts, aliases/nested roots, unavailable metadata, notifications and
idempotence. Use synthetic accounts/tenants and no customer documents/model calls
where deterministic fixtures suffice. Verify real delivery/providers where claimed.

Hold affected rollouts on core-journey or security regressions. Recover prior
compatible code/locks or use the prepared forward-recovery procedure; never
blindly roll back data or delete legacy records. Retain tested artifacts.

Current means latest stable compatible and verified at the start of a wave; later
releases enter the next reconciliation. Uniform means predictable behavior with
supported product themes and domain adapters. Existing maintenance administration
must be tested before asking the owner for another login.

Completion requires: a complete census with dispositions, verified deployments
for applicable apps, passed identity/security migrations, completed observations,
reconciled public claims, and a second automated release/update cycle. Report
retained exceptions and external blockers explicitly. An inaccessible, blocked or
unverified subset prevents an unqualified claim that everything is complete.
